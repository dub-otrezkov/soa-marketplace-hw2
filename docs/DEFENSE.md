# Подготовка к защите — 20 минут

Сначала прочитайте [условие](assignment.md), затем запустите сценарий самостоятельно. Успешный E2E подтверждает поведение стенда, но на защите нужно уметь объяснить решения и менять входные данные.

## План демонстрации

| Время | Что показать |
|---|---|
| 0–3 мин | `docker compose up --build --detach --wait`; логи запуска, PostgreSQL, Flyway, health |
| 3–8 мин | `bash scripts/demo.sh`: регистрация, товар, промокод, заказ, snapshot, изменение, отмена; реальные SELECT |
| 8–12 мин | альтернативные сценарии: валидация, чужой заказ, недостаток остатков, запрещённый переход; E2E |
| 12–16 мин | OpenAPI → сгенерированный интерфейс/DTO → контроллер → сервис → SQL; транзакция и блокировки |
| 16–20 мин | 2–4 теоретических вопроса, ответы ниже |

Образы и зависимости стоит скачать заранее; перед демонстрацией оставить время на фактический запуск, а не рассчитывать на мгновенную сборку. Демо запускается повторно с новыми именами и не удаляет предыдущие записи.

```bash
docker compose up --build --detach --wait
docker compose ps
docker compose logs --tail=80 api
bash scripts/demo.sh
python3 scripts/e2e.py --db-checks
```

Можно выполнить отдельный сценарий, например:

```bash
python3 scripts/e2e.py MarketplaceE2E.test_07_update_failure_restores_previous_order
python3 scripts/e2e.py MarketplaceE2E.test_14_concurrent_stock_reservation
python3 scripts/e2e.py --db-checks MarketplaceE2E.test_13_active_order_and_error_ordering_with_db
```

`--db-checks` использует локальную БД Compose: делает SELECT и адресно меняет только созданные данным запуском тестовые записи для проверки времени cooldown и отключённого промокода. Эти изменения подробно описаны в README. При демонстрации реального ожидания можно выполнить второй запрос после `ORDER_COOLDOWN_MINUTES` минут вместо изменения времени в БД.

Для HTTP-проверки истёкшего JWT дополнительно задайте `JWT_SECRET` локального стенда по инструкции README. Тест создаёт собственный подписанный fixture с прошлым `exp`, не переводит часы и проверяет именно `TOKEN_EXPIRED`, а не ошибку подписи. Без этого параметра проверка истечения пропускается; неверные токены и ротация проверяются в любом случае.

## SQL, который надо понимать

Войти в PostgreSQL:

```bash
docker compose exec db psql -U marketplace -d marketplace
```

Замените `123` / `456` / `789` на ID из ответа API. Эти запросы читает и выполняет сам студент; они показывают сохранение данных, а не только HTTP-ответ.

```sql
SELECT id, name, price, stock, status, seller_id, created_at, updated_at
FROM products WHERE id = 123;

SELECT id, user_id, status, total_amount, discount_amount, promo_code_id
FROM orders WHERE id = 456;

SELECT product_id, quantity, price_at_order
FROM order_items WHERE order_id = 456 ORDER BY product_id;

SELECT code, discount_type, discount_value, max_uses, current_uses
FROM promo_codes WHERE id = 789;

SELECT operation_type, created_at
FROM user_operations WHERE user_id = 123 ORDER BY created_at;

SELECT indexname, indexdef FROM pg_indexes
WHERE tablename IN ('products', 'orders');

SELECT installed_rank, version, description, success
FROM flyway_schema_history ORDER BY installed_rank;
```

До заказа stock равен 5; после заказа трёх единиц — 2; после отмены снова 5. `price_at_order` остаётся 100, даже если `products.price` изменён на 150. При мягком удалении строка товара остаётся, `status = ARCHIVED`. После отмены `current_uses` уменьшается; повторная отмена запрещена и не возвращает склад второй раз.

## Объяснение ключевого кода

**Contract-first.** В `src/main/resources/openapi/marketplace.yaml` определены пути, запросы, ответы, ограничения, security и ошибки. Maven OpenAPI Generator создаёт интерфейсы и DTO. Контроллер реализует сгенерированный интерфейс; ручной параллельной модели запроса нет. Правка контракта требует новой генерации и компиляции, поэтому рассогласование виднее при сборке. Генератор сам не реализует транзакции и бизнес-правила.

**Путь запроса.** Фильтр назначает request_id, JWT-фильтр проверяет подпись, срок действия и тип токена, Spring связывает JSON со сгенерированным DTO, Bean Validation проверяет ограничения, контроллер вызывает сервис, сервис проверяет роль и владельца и выполняет SQL. Advice возвращает единый ErrorResponse. Фильтр записывает итоговый HTTP-статус, длительность и request_id в JSON-лог; пароль и токены не должны попадать в открытом виде.

**Атомарность.** В `OrderService` `@Transactional` объединяет резервирование, строки заказа, промокод и запись операции. Исключение вызывает rollback. Проверка остатков без блокировки недостаточна: два запроса могут увидеть stock=1 и оба продать его. `SELECT … FOR UPDATE` удерживает блокировку до commit/rollback. На update учитывается доступный остаток плюс собственный старый резерв, затем применяется разница; внешние транзакции не видят промежуточный возврат.

**Конкуренция.** Порядок блокировок общий: пользователь → заказ → товары по ID → промокод. Это снижает риск взаимных блокировок. Строка пользователя берётся через `FOR NO KEY UPDATE`: два первых заказа не проходят проверку одновременно, а проверка внешнего ключа совместима с этой блокировкой. Partial unique index дополнительно защищает инвариант одного активного заказа. Для промокода проверка лимита и инкремент проходят под одной блокировкой. Три E2E-гонки проверяют эти случаи; ещё одна проверяет однократную ротацию refresh token.

**Порядок ошибок.** CREATE: cooldown → активный заказ → каталог → остатки → промокод. UPDATE: владелец → состояние → cooldown → каталог/остатки → пересчёт. Сначала отсутствующий товар/неактивный каталог, потом нехватка остатков. Валидация JSON и авторизация происходят ещё до бизнес-проверок. Неудачная операция не оставляет запись cooldown.

**Состояния.** Нормальный путь: CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED. Отмена разрешена только из CREATED/PAYMENT_PENDING. Менять состав можно только в CREATED. ADMIN переводит состояние через отдельный PATCH; прямой CREATED → SHIPPED получает 409.

**Деньги и промокоды.** Используются NUMERIC(12,2) и BigDecimal, а не float/double. У существующих позиций при update сохраняется snapshot, у новых берётся текущая цена. Процент выше 70 означает нулевую скидку по буквальному тексту условия; ровно 70 работает. Применённый к заказу промокод не расходуется повторно при update. При падении суммы ниже minimum промокод снимается, счётчик уменьшается. Неактивный/истёкший промокод вызывает rollback обновления. Эти трактовки стоит озвучить до пограничного примера.

**JWT.** Подпись обеспечивает целостность, но не шифрует payload. В claims есть идентификатор пользователя, роль, тип и срок токена. Access — 20 минут, refresh — 14 дней. Refresh нельзя использовать как access. При обновлении старый refresh отзывается, клиент получает новую пару; блокировка записи запрещает повторное параллельное использование. Пароль хранится как BCrypt-хеш. Публичная регистрация не выдаёт ADMIN. Проверка роли не заменяет проверку владельца ресурса.

## Ответы на 16 вопросов

1. **Основные принципы REST; зачем stateless?** Клиент и сервер разделены; каждый запрос содержит достаточно контекста; ответы указывают возможность кэширования; интерфейс единообразен; допустимы промежуточные слои; code-on-demand необязателен. Stateless означает отсутствие обязательной серверной сессии разговора с клиентом, а не отсутствие БД. Самодостаточный запрос можно направить любому экземпляру сервиса, что упрощает масштабирование и восстановление.

2. **Что такое ресурс и как проектировать URL?** Ресурс — адресуемая сущность или коллекция: товар `/products/42`, список `/products`. URI идентифицирует ресурс, метод задаёт действие. Для фильтров и пагинации подходят query-параметры. В проекте `/orders/{id}/cancel` — явно заданная условием команда жизненного цикла; это практический компромисс, который следует объяснить.

3. **Какие HTTP-методы соответствуют CRUD?** POST обычно создаёт ресурс, GET читает, PUT задаёт новое представление изменяемых полей, PATCH частично меняет, DELETE удаляет ресурс или его доступность. Здесь DELETE архивирует товар по условию, а PUT заменяет поля ProductUpdate или весь состав заказа. GET не должен менять бизнес-данные.

4. **Что такое идемпотентность?** Повтор одного запроса приводит к тому же предполагаемому состоянию, что и один запрос; ответы могут различаться. GET, PUT и DELETE имеют идемпотентную HTTP-семантику, POST обычно нет. В нашем API повтор PUT заказа может получить 429 из-за журнала операций, не меняя второй раз бизнес-данные. Надёжный повтор создания заказа в производственной системе потребовал бы отдельного idempotency key и сохранения результата, чего это задание не требует.

5. **Что такое OpenAPI?** Машиночитаемое описание HTTP API: пути, методы, параметры, схемы, ответы, ошибки, авторизация. Из него можно создать документацию, клиенты, интерфейсы серверов и DTO. Контракт не доказывает, что реализация соблюдает правила: это проверяют валидация и тесты.

6. **Что означает contract-first?** Сначала согласуется контракт, затем из него генерируются интерфейсы и модели, после чего пишется реализация. Клиент и сервер могут разрабатываться параллельно; ограничения и ошибки видны заранее. Важно версионировать изменения и не редактировать сгенерированные файлы вручную.

7. **Какие HTTP-коды ответов используются?** 200 — успешный ответ, 201 — создан ресурс, 204 — успех без тела; 400 — некорректные данные, 401 — нет действительной аутентификации, 403 — недостаточно прав, 404 — ресурс отсутствует, 409 — конфликт состояния, 422 — семантически неприменимый промокод, 429 — ограничение частоты, 500 — внутренняя ошибка. Машиночитаемый error_code уточняет бизнес-причину.

8. **REST и gRPC: различия и выбор?** REST моделирует ресурсы и представления, обычно использует HTTP/JSON. gRPC моделирует RPC-методы через protobuf-контракт, поддерживает строгую типизацию и потоковые вызовы. HTTP/JSON удобен для публичных API и ручной диагностики; gRPC часто удобен внутри контролируемой инфраструктуры. Выбор зависит от клиентов, streaming, совместимости, наблюдаемости и измерений; gRPC не отменяет ошибки сети и связанность синхронных вызовов.

9. **Проблемы синхронного взаимодействия?** Суммируются задержки; недоступность зависимостей распространяется по цепочке; заняты соединения и потоки; ретраи могут умножить нагрузку и повторить запись. Нужны timeout, ограниченные retries с backoff/jitter, идемпотентность, circuit breaker и ограничения параллелизма. Для независимых процессов часто подходит очередь событий.

10. **Частые ошибки проектирования REST API?** Изменение данных через GET, неясные ресурсы, неверные коды ответа, несогласованные ошибки, отсутствие ограничений пагинации, пропуск проверки владельца, доверие user_id из JSON, несовместимые изменения контракта. Отдельная проблема реализации — проверять stock отдельно от транзакционного резервирования.

11. **HATEOAS: что и зачем?** Сервер возвращает ссылки и допустимые действия вместе с представлением, чтобы клиент обнаруживал переходы из текущего состояния. Например, созданный заказ мог бы содержать ссылки на оплату и отмену, а завершённый — нет. Это уменьшает жёсткое знание маршрутов у клиента. В данном учебном API переходы описаны в OpenAPI; HATEOAS-ссылки не реализованы.

12. **Что такое short polling?** Клиент регулярно запрашивает состояние и сразу получает текущий ответ. Это просто, но даже при отсутствии изменений создаёт запросы, а задержка обнаружения зависит от интервала. Подходит для редких обновлений и небольшого числа клиентов.

13. **Чем long polling отличается?** Сервер удерживает запрос до изменения или timeout, затем отвечает, а клиент открывает следующий запрос. Пустых ответов обычно меньше, изменения видны быстрее, но нужно управлять числом открытых соединений, таймаутами и повторным подключением. Это не бесконечный двусторонний канал WebSocket.

14. **Почему REST — стиль, а не протокол?** REST задаёт архитектурные ограничения и свойства взаимодействия; HTTP задаёт конкретные правила передачи, методы и коды. JSON поверх HTTP ещё не означает соблюдение всех ограничений REST. Архитектор выбирает ресурсы, представления, кэширование и переходы, а протокол обслуживает передачу.

15. **Почему синхронные вызовы повышают связанность?** Для завершения операции вызывающий сервис зависит от доступности и времени ответа вызываемого прямо сейчас. В цепочке увеличивается число обязательных одновременных участников. Асинхронная очередь ослабляет временную связанность, но добавляет eventual consistency, дубликаты и необходимость обработки повторов.

16. **Почему REST может быть неудобен в high-load межсервисном взаимодействии?** Это не безусловный запрет. Частые мелкие HTTP/JSON-запросы и длинные синхронные цепочки расходуют сеть/CPU и увеличивают хвостовые задержки. Можно применять кэширование, batching, пулы соединений, компактные форматы, gRPC или события. Решение выбирается по профилированию и требованиям; REST может успешно работать под высокой нагрузкой, а замена формата сама по себе не исправит чрезмерную связанность.
